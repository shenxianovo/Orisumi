## 原则

**初值 + 变化 = 任意时刻的状态。** 下面每一条都是为了让这个等式成立。

### 先定对象

每类对象一张身份表，记它是谁，以及永远不变的属性。比如下载的 URL 和开始时间、书签的创建时间。

不变的属性一开始可能不知道，后来可以从未知补成已知；已知之后不再改。

### 会变的属性只记初值和变化

第一次看到时记一行初值，之后只在值变了才记。值没变不写。

能一起记的放一张表，否则拆开。判断标准：来源会不会单独改、或单独缺其中一个。

- 下载的状态和完成时间总是一起变：放一张表。
- 下载的本地路径会单独变：单独一张表。
- 回合的开始时间不变，结束时间后来才有：开始时间放身份表，结束时间单独记。

拆对了，每张表的一行都能用一句话说清：“某对象的某组属性，在这次观测时变成了这个值”。

### 事件每次发生都记

按键、休眠、网页访问没有“当前值”，发生一次记一行，不去重。重试送来的同一次发生，靠事件 ID 去重。

### 未知和空要分开

NULL 只表示“不知道”，与 SQL 本身对 NULL 的理解一致。“知道它是空的”要写成明确的值。

| 情况 | 怎么记 | 例子 |
| --- | --- | --- |
| 读到了值 | 写这个值 | 窗口标题是 `README.md` |
| 读到了，来源明确说没有 | 写明确的空：文本（含来源 ID）用 `''`；外键或数字列加一列 `has_*` | 标题为空写 `''`；没有前台应用写 `has_app = 0` |
| 这次读不到 | 写一行 NULL，算一次变化 | 辅助功能权限丢了，读不到标题 |
| 来源这次没提这个字段 | 不写，沿用上一个值 | Chrome 下载回调只带了状态，没带路径 |
| 从没观测过，或采集断开 | 没有行；断开记在 `capture_runs` 和覆盖记录里 | 采集器启动前的情况 |

“读不到”必须写一行。不写的话，`current_*` 会一直显示上一个已知值，好像它仍然成立。

例外：某列在当前状态下本来就没有值，比如下载未完成时的完成时间、成功运行的错误信息。这时把它和决定它的列放在同一张表，用 `CHECK` 绑定两者；除此之外，NULL 一律是未知。

来源自己不区分“没有”和“读不到”时（比如应用的 bundle ID 返回 nil），只能记 NULL。

### 时间分两种

- `observed_at_utc_ms`：本地收到通知或读到来源的时间。
- 来源自己给的时间，按含义命名，例如 `visited_at_utc_ms`、`started_at_utc_ms`。来源没给就是 NULL，不拿观测时间顶替。

本库的自增 ID 和 `run_sequence` 只保证本库内的先后。

### 断开后重新起头

等式只在一条不断的观测链上成立。采集器停了、权限丢了、电脑休眠了，中间发生了什么我们不知道。如果直接接着记，查询会把断开的那段当成“没变”。

- 每段连续观测有自己的初值。恢复后能补读就先补读；补不齐就记下缺口，再重新记初值。
- `capture_runs` 记每段采集的起止。结束时间和 `stop_reason` 一起写，失败时 `error` 才有值。异常退出时两者都留空，表示未确认，不用重启时间或查询时间补。
- 运行中也可能缺权限、通道不可用、采样漏掉短暂变化，这些另外记。所以采集在运行，不等于全程都看到了。
- 没有新变化，只在链没断的前提下才能说明状态没变。

## 从哪里取数据

每类事实单独选取数方式，按这个顺序优先：

| 来源能力 | 怎么采 | 断开后怎么恢复 |
| --- | --- | --- |
| 可回放的日志 | 先回填，再按读取位置增量读 | 从已提交的位置接着读；来源已经删掉的部分记为缺口 |
| 变更通知 | 记初值，然后接上通知，记每次变化 | 重放还没送达的通知；补不了的区间记为缺口，重新记初值 |
| 只能读当前值 | 定时读，和上次比，变了才记 | 记下采样边界，恢复后重新记初值 |

后两种得到的“变化”可信度不同。通知送来的变化，时间接近真实。读当前值比出来的变化，只能说明“读的时候已经变了”：时间是读取时间，两次读取之间的 A→B→A 会整个丢掉。通知只说“有变化”、要再去读值时，读到的结果也属于后一种。用了后两种的，在[采集数据](./sources.mdx)写明丢什么。

**初值和通知要接上。** 先订阅通知并缓存，再读快照，然后把快照之后的通知接上。顺序反了，读快照和开始监听之间的变化会丢。来源做不到原子衔接时，用序号、重试或读后核对补上。

**定期核对**只用来纠正当前状态、发现漏掉的通知；值没变就不写。它补不出断开期间的 A→B→A。批量写入、重试、超时这些定时器和采样频率分开设置。

## 写入与恢复

- 一次观测产生的几条事实，在同一个事务里提交，各表的行共享同一个观测标识。读取游标和事实一起提交，否则会出现游标前进了但事实没写，或反过来。
- 保留能回到来源核对的上下文，比如日志的文件和行号、来源对象的 ID。
- 重试不能重复入库。跨进程投递用稳定的事件 ID；接收端提交后再确认，确认后才从持久队列删除。确认丢了，重发也安全。
- 日志游标记文件身份和读取位置，要处理截断、替换、移动和末尾的半行。文件变化通知只用来触发读取，事实以文件内容为准。
- 输出库重建后，读取游标和发送端的基线都作废：能回放历史的来源重新回填，其余重新记初值。
- `_collector_state`、`_token_usage_rollouts`、读取游标、待发队列是采集进度，可以原地更新，不算历史事实。

## 查询视图

- `*_history` 给出每次观测后的完整状态；`current_*` 给出最后已知状态。
- 最后已知状态不说明来源现在还在、还能读到。
- 需要缓存时，缓存必须能从事实表重建。
- 不同来源库的本地 ID 不能直接关联。跨来源关联时核对设备、对象生命期和时间。

## 数据库结构

每个来源写一个独立的库：`STORE/raw/<来源>.sqlite`。结构定义放在采集器项目的 `Schema/`：

| 路径 | 内容 |
| --- | --- |
| `Tables/` | 每张表一个 SQL 文件，含字段、键和约束 |
| `Indexes/` | 普通索引，按所属表分文件 |
| `Views/` | 每个视图一个 SQL 文件 |
| `Version.txt` | 该来源的结构版本，正整数 |

构建时自动收集这些文件，按表、索引、视图的顺序执行，同组按文件名排序，不用登记清单。这些文件只定义结构；导入时用的临时视图留在采集代码里。

C# 用共享的 `Collectors/Storage/SqliteSchema.cs` 加载程序集内的 SQL。Swift 用 `Native/DatabaseSchema.swift` 加载可执行文件旁边的 `Orisumi.Collectors.MacOS/Schema/`，由构建和发布负责复制。

初始化只接受两种库：没有任何用户对象的空库，或版本相同的库。空库就建结构并设置 `PRAGMA user_version`；版本不同就报错，失败时回滚。外键和锁等待在打开连接时设置，WAL 在事务外设置。

结构一改就加版本号。不做迁移：版本不匹配时，停掉对应采集器并重建它的库。macOS 库总是建完整结构，选项只控制哪些通道采集和写入。

## 开发与验证

1. 每类事实先想清楚：对象身份、取数方式、时间含义、能还原到什么程度。
2. 先做好初值衔接、提交确认和中断恢复，再接启动和查询。
3. 按实际风险测：A→B→A、静止时不重复写、重复投递、提交前后崩溃、恢复后的缺口。日志来源另测半行、替换和截断；采样来源另测计数重置和身份变化。
