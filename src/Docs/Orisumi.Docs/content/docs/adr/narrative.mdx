## 背景 [#context]

Web 控制台打开一天时，先显示这一天做了哪几件事，例如“上午重新审视 Observer 与 Runtime 的模型，晚上让 Codex 把代码改到新模型”。这些话来源给不出，要由模型读当天的记录写出。叙事是私有理解，保存为 Observation，见 [UNDERSTANDING-3](../core/rules/understanding.mdx#understanding-3)。

模型写一整天要半分钟左右，用户要看着几件事一件件出现，所以页面和调用模型的一方之间需要一条同步的请求。服务器上的 Observer 由 Runtime 运行，见 [ADR · Runtime 与进程托管](./observer-runtime.mdx)，页面连不到它们。

## 决定 [#decision]

- 一件事是一份 [Episode](../observers/narrative/episode.mdx) Observation：事实时间是这件事的时段，内容是标题、摘要以及涉及的会话和本机应用，形成方式是推断，InputSet 列出写它时读到的版本。
- 叙事 Observer 是一个程序实例，由 API 进程托管。它的 EntityId 由后端保存，每个部署一个，它不经过 Runtime 安装和管理。
- Web 控制台请求写某一天时，叙事 Observer 读这一天的记录，调用 OpenAI 的模型，每写完一件事就推给页面；全部写完后，一次写入这一批。
- 重写一天时写新的一批，再为被替换的每件事写一份 `supersede` 的 Review。
- 用户否定写错的一件事。重写时叙事 Observer 读到否定，模型不再写出这件事。
- API Key 和模型由 API 进程的运行环境提供。

## 理由 [#rationale]

流式需要页面发出请求、等着结果一件件回来。API 进程本来就接收页面的请求，也能直接读写数据，叙事 Observer 放在这里，路径最短。它只在被请求时工作，不需要安装、启停和远程管理，所以 Runtime 的托管能力对它没有用处。

一件事一份 Observation，用户才能只否定写错的那一件，会话和本机应用的档案才能经由引用连到它所在的事。写完再一次写入，页面看到的几件事和保存下来的就是同一批，写到一半失败时什么都不保存。

放弃的方案：

- **Runtime 上的叙事 Observer，定时写好。** 页面打开时直接读，但看不到写的过程，刚发生的事要等下一轮。
- **浏览器直接调用模型，Web 控制台作为 Observer 写入。** API Key 要交给浏览器，控制台从读取方变成写入方。
- **一天一份完整的文字。** 不能逐件否定，会话也连不到它。

## 代价 [#costs]

- API 进程依赖 OpenAI：要配置 API Key，每写一天都有费用。没有配置时，叙事不可用，其他接口不受影响。
- 叙事 Observer 随 API 发布和升级。
- 写一天要等半分钟左右，这段时间 API 进程占着一个模型请求。
- 写下的几件事引用当时的会话和本机应用；会话之后又有新的交互，几件事不会自动更新，要用户重写。
