## 背景 [#context]

观测可能在事实进行中形成，随后不断延长；填错的边界或时区需要纠正。两个 Observer 可能读到同一条来源数据，来源还可能缺少时间。

没有统一规则，同一个事实会重复保存，旧值会被覆盖，读取方也分不清“同一句话的新说法”和“另一份观测”。

## 决定 [#decision]

- 业务规则决定事物的身份和 Observation 的粒度。
- 事实时间未知时保持未知。
- 后端在保存每份 Observation 时赋值保存时间。
- 同一识别依据内容相同时什么都不发生，内容不同时保存新的一份，替换这个依据最新的一条。写入方也可以显式声明替换。
- 独立的陈述形成新的 Observation，包括用另一种方法对同一份证据的独立解释。
- 识别依据全局有效。各说各的内容把作者放进 `scope`。

## 理由 [#rationale]

只有业务规则能说明来源的含义，例如两次读数之间应用是否一直在前台。后端按内容合并或拆分，会把巧合当成同一个事实。

保存时间回答“后端什么时候保存了这一份”。

旧的一份已经保留，禁止纠正不能进一步保护历史，只会逼写入方删除重建或绕开模型。所以新的一份可以延长时段，也可以修正错误，只需自身合法。

重读和程序升级本身不决定观测的身份。例如把工具结果误记成用户发言，修复后重读，陈述的还是原来那件事，所以新的一份替换原来的；换一个模型重新评价当天的活动，是一次新的判断，所以形成新的观测。

识别依据全局有效，重装后的新实例重读日志时，内容相同什么都不发生，数据不会翻倍。比较时不看是哪个 Observer，所以设备描述这样的全局状态只有一条当前的说法，不用按 Observer 各写一份。

放弃的方案：

- **后端按内容去重或合并。** 内容相同不说明是同一次观测，内容从 A 改成 B 再改回 A 也有独立意义。
- **用其他时刻填补未知的事实时间。** 读取方会分不清“确实在这一刻”和“不知道是什么时候”。
- **已保存的观测只能单调补全。** 历史已经保留，这条限制只会阻止纠正。
- **按客户端时间戳决定最新的一条。** 时钟不同步时，晚到的旧写入会覆盖新内容。
- **在 Core 中定义纠正操作。** 纠正就是再说一句。

## 代价 [#costs]

- 需要沿用的 `thingId` 必须持久保存，例如程序实例。
- 写入方写入的旧内容后到时，会成为这个依据最新的一条。重发被拒绝的写入时要注意这一点。
- 同一依据写入的内容不同时后端都接受，Codex 早期的 `item-N` 只在一个会话内唯一，这类身份冲突不会被拒绝，要靠写入结果的 `replaced`、替换链和测试发现。拒绝不同内容的代价更大：读取进度丢失后重读，`timeZone` 变化也会被拒绝。
