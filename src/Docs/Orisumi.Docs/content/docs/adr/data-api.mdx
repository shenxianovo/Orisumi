## 背景 [#context]

Core 定义了事物、Observation 和写入的语义，HTTP 接口要把它们表示出来。读取方要能沿引用读到一份 Observation，写入方要能交出一份 Observation 的完整内容。语言模型是主要的读取方之一，一次查询要能拿到可读的内容。后端还要判断交来的内容和已有的是否相同，而同一份 JSON 可以有多种写法。读取方还要能从一个事物出发，看到它现在的样子和发生过的事；引用只保存在引用方（[REFERENCE-4](../core/rules/references.mdx#reference-4)），读取方自己无从得知谁引用了它。

## 决定 [#decision]

- 接口按身份寻址：Observation 用 `observationId`，事物用 `thingId`。所有业务类型共用同一组路由。
- 资源名只作为筛选参数，不进入路径。
- 查询 Observation 直接返回内容，默认是默认视图，`view=all` 返回全部。按 id 读取不经过默认视图。
- `GET /things/{thingId}` 是对象视图：现在的样子、关系、发生过的事的计数和分页入口，以及名字。
- `GET /search` 在 `searchable` 字段中查找文字，第一版是子串扫描。
- `POST /runs` 开始一次工作，读取时带上它，写入时由后端形成 InputSet。
- 事物有单独的列表和批量读取，每个事物带着名字。
- 按事实时间查询 Observation 时，只看已知的边界。两个边界都未知的 Observation 不参与时间查询。
- 写入只有一个接口，一个请求是一组有序的写入，见 [ADR · 单向写入与托管的分工](./data-capability.mdx)。响应逐个列出每次写入的结果，被拒绝的写入不影响其他写入。
- Observation 的 JSON 成员与 Core 的成员一一对应。
- “内容相同”按 JSON 的值判断：对象不讲键的顺序，数字按数学值比较，时间换算为 UTC 并截断到微秒后再比较。
- 反查按目标 id 精确匹配，只返回直接的引用方，每一项是引用方的完整 Observation 和其中引用目标的位置（JSON Pointer）。目标已删除时照常列出引用方。
- 请求本身有错时返回 `400`，与已保存的数据冲突时返回 `409`。被 Core 规则拒绝时，错误响应带规则编号 `rule`。
- 读取从未出现过的身份返回 `404`，读取已删除的事物或 Observation 返回 `410`。删除已删除的数据视为成功。
- 删除 Observation 和事物返回移除的内容和依据被删除内容的 Observation。

## 理由 [#rationale]

引用只保存 id，读取方沿引用读取时只知道这个 id，所以读取不能要求先给出类型。后端按 Observation 自己的 `schemaRevisionId` 校验内容，路径中的类型只会重复这项信息。资源名的格式也允许以 a 到 f 开头的 UUID，放进路径就无法和 id 区分。资源名作为筛选参数时，同一个参数在各处含义相同。

未知的边界按无界处理时，一份“开始未知、结束于 10 月 5 日”的 Observation 会出现在 10 月 5 日之前任何时间范围的查询中。只看已知的边界，结果中的每份观测在查询范围内都有已知的时间。

事物本身读不到内容，所以读取接口把名字带上，显示一批设备或会话时不用逐个查询。

默认视图由后端筛选，因为它要看每条陈述的复核、替换和代，读取方自己做要逐条反查，见 [ADR · 不可变的 Observation](./immutable-observations.mdx)。按 id 读取是追溯，要读到当时的内容，所以不经过它。

用户操作的是对象。对象视图靠 `role` 把引用分成三堆，所以后端不用认识具体的业务类型。发生过的事可能有几十万条，所以只给计数和入口。

Agent 要知道的是它用了哪些数据，这只有读取时才知道。读取由系统记下，写入时不用 Agent 自己列，依赖链就由结构保证。

一个请求可以同时含有多次写入，没有单个新建的资源，所以统一返回 `200`，逐个列出结果。

JSON 对象本身无序，数字也有多种写法。按文本比较时，同一份内容换一个序列化库，就会被判为不同。时间在保存时换算和截断，比较也在同一种表示上进行。

反查每一项带上完整的 Observation，读取方不用再逐个读取；带上位置，读取方才能区分关系，例如同一个事物在一份 Observation 中是 Observer，在另一份中是被提到的对象（[REFERENCE-2](../core/rules/references.mdx#reference-2)）。

只返回直接的引用方，因为每一层的关系含义不同：从 VS Code 到前台时段是“哪个应用”，从前台时段到推断是“读过这一段”，读取方按需要决定沿哪些关系走多远。目标被删除后，引用方仍是用户的数据，照常列出，读取方才能说明哪些追溯不完整（[HISTORY-8](../core/rules/history.mdx#history-8)）。

`409` 的请求换一个时机可能保存成功；`400` 的请求本身需要修改。规则编号比状态码细，写入方和 Agent 按它判断具体原因，所以违反规则和不符合契约共用 `400`，由 `rule` 区分。

删除的身份保留着，区分 `404` 和 `410` 不需要额外的存储。读取方沿引用追溯到 `410` 时，可以说明这项数据已被用户删除（[HISTORY-8](../core/rules/history.mdx#history-8)）；`404` 说明引用的目标从未存在，数据有误。

放弃的方案：

- **按类型分路由，例如 `/observations/{resourceName}/{id}`。** 沿引用读取时不知道类型。
- **每个操作单独一个请求。** 导入大量数据时请求数过多。
- **未知的边界按无界处理。** 时间查询会返回大量时间实际不在范围内的观测。
- **按序列化后的文本比较内容。** 比较的结果会取决于写入方使用的 JSON 库。
- **反查只返回引用行，不带内容。** 读取方几乎总要读内容，每一项都要再发一次请求。
- **反查一次返回全部间接的引用方。** 结果混在一起，分不出每一层是什么关系，数量也难以预计。
- **读取事物时不带名字。** 显示一个列表要先读事物，再逐个查 Name。
- **目标已删除时返回 `410`。** 读取方查不到还有哪些数据引用着它。
- **违反规则时返回 `422`。** 多一个状态码，区分的信息已经由 `rule` 提供。
- **已删除和从未出现都返回 `404`。** 读取方分不清用户的删除和数据错误。

## 代价 [#costs]

- 读取一份 Observation 前不知道它的类型，读取方要看 `schemaRevisionId` 再解释内容。
- 两个边界都未知的 Observation 只能按类型或事物找到。
- 读回的内容不保留键的顺序和数字的原始写法。需要保留原文的来源，把原文保存为字符串字段。
- 规则编号成为接口的一部分，写入方按编号判断原因。
- 读取方能知道一个身份曾经存在、后来被删除。
- 跨越多层的反查，读取方要逐层发请求。
- 引用位置中的数组下标按保存时的顺序。
