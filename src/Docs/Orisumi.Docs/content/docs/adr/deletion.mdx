## 背景 [#context]

Orisumi 保留每一份 Observation 用于追溯，用户也要能删除自己的数据。需要划清删除移除什么、留下什么，以及被删的内容还被引用时怎么办。判断错了时用否定，删除只用于用户要抹掉的数据，见 [ADR · 模型形成的理解](./understanding.mdx)。

程序可能还持有已删除事物的 `thingId`，来源也可能被整份重读。删除后如果还能写入，这些请求会把删掉的数据重新建出来。

## 决定 [#decision]

- 删除一份 Observation，沿 `replaces` 把被它替换的说法一起删除。
- 删除一个事物，移除以 `about` 和 `part` 引用它的 Observation，连同它们的替换链；`mention` 的引用保留，目标不可读取。
- 后端返回依据被删除内容的 Observation 列表，这些陈述保留，读取时标记不可读取。
- 被删除的事物不再被引用。`thingId` 和 `observationId` 不再分配。
- 识别依据留下不含内容的墓碑，写入时命中就跳过，重读来源不能恢复已删除的内容。
- 被删除的内容不留副本。不再有 Observation 使用的二进制内容同时移除，见 [ADR · 二进制内容](./binary-content.mdx)。
- 仍有事物或 Observation 使用某个 Schema 或事物类型时，不能删除它。
- 删除受管理的程序实例时，同时结束它的管理登记；还没写入过的程序实例也可以删除，它的 `thingId` 之后不能再使用。
- 派生文字里的残留是已知局限，删除后用搜索找出可能残留的位置。

## 理由 [#rationale]

“Observation 不可改写”和“用户可以删除”两条要求可以同时满足：前者禁止替换内容，后者让内容不可读。用户删除数据的权利优先于追溯。

只删除替换链上最新的一份时，上一份说法就复活了，用户看到的是被自己删掉的内容的旧版。所以沿 `replaces` 一起删。

删除一个人或一个会话时，用户要抹掉的是这个对象本身：`about` 是关于它的话，`part` 是它的一部分。`mention` 只是提到它，那份 Observation 说的是别的事，保留。`role` 由 Schema 声明，所以后端不用认识具体的业务类型。

重读来源时已删除的内容不能回来，否则用户每次删除都要和重读竞争。墓碑不含内容，所以它不算副本。

推断、摘要这类派生文字可能引用或转述被删除的内容。自动判断要理解文字，所以后端列出依据被删除内容的陈述，用户决定怎样处理。

Schema 还有数据依赖时不能删除，保留的数据才能按原定义解释。

程序实例的身份在它第一次写入之前就由 Runtime 分配。用户删除这样的实例，是要它以后不再以这个身份写入，所以它的 `thingId` 和已删除的事物一样不能再使用。

放弃的方案：

- **删除后允许以同一个身份重建。** 离线补发的旧请求会撤销删除。
- **软删除，保留内容并标记删除。** 删除的数据仍然留在系统中。
- **删除时沿全部引用连带删除。** 会删掉用户没有选择的数据。
- **识别依据随删除移除，重读时作为新对象创建。** 用户删掉的内容会在下一次重读时回来。
- **为追溯在别处保留副本。** 违背用户的删除。

## 代价 [#costs]

- 输入被删除后，依赖它的观测无法完整追溯。
- 删除一种类型的全部数据需要两步。
- 被删除的身份永久不能再用。删除身份的保存、查询和空间回收由存储设计决定。
- 墓碑永久占用空间。用户想让同一个来源对象重新进入，当前没有入口。
- 删除一个对象后，属于它的新数据不再保存。只是提到它的数据继续保存，引用不可读取，所以删除一台设备不影响之后的采集。
- 派生文字里的残留靠搜索发现，字面没有命中的转述找不到。
