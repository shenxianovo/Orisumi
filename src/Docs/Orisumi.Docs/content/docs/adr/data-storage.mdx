## 背景 [#context]

后端要在 PostgreSQL 中保存所有类型的 Observation 和它们用到的二进制内容，按身份、类型和事实时间读取它们，算出默认视图，并记住已删除的身份。业务类型的数据量相差几个数量级：键鼠事件一天几千条，有些类型一天只有几条。业务类型的字段随 SchemaRevision 变化，引用可以嵌在对象和数组中，读取方还要能按目标找到引用方。多个请求可能同时处理写入和删除。

## 决定 [#decision]

- 权威数据有九张表：`observations`、`things`、`deleted_observations`、`schema_revisions`、`thing_types`、`input_sets`，`contents` 保存二进制内容的字节，见 [ADR · 二进制内容](./binary-content.mdx)，`recognition_keys` 保存识别依据，见 [ADR · 单向写入与托管的分工](./data-capability.mdx)，`key_tombstones` 保存已删除的依据的摘要。
- `schemas`、`observation_references`、`observation_contents`、`replacements`、`reviews`、`same_as_links` 和 `adoptions` 是查询投影，可以从权威表重建。权威表不设置指向投影的外键。
- 所有业务类型的 Observation 保存在同一张表中，业务字段以 `jsonb` 保存，Observation 的成员是列。
- 命题键、状态键和可搜索的文字在保存时算出，存在列中。
- 按类型和事实时间的查询，使用以类型开头的索引。
- 删除 Observation 时把身份写入 `deleted_observations`，永久保留，不保存删除时间。删除事物时保留 `things` 的行，标记已删除。识别依据只留摘要。
- `observation_references` 每行记录一份 Observation 引用了一个目标和角色，不记录位置。API 返回的位置在读取时从内容中重新算出。
- 默认视图在查询时算出，不保存结果。
- 一次工作的读取记录保存在 `runs` 和 `run_reads` 中。
- 所有操作串行执行。一个写入请求在一个事务中完成，每次写入一个保存点。
- 后端的另外两张表是 Observer 的管理登记，不属于 Core，见 [ADR · Observer 的统一管理](./observer-management.mdx)。

## 理由 [#rationale]

业务字段随 SchemaRevision 变化。按字段建列，每出一条修订就要改表，嵌在对象和数组中的引用也放不进列。以 `jsonb` 保存，每份 Observation 按写入时的结构原样保存，按它引用的修订解释。Observation 的成员由 Core 固定，所以是列，时间也不用在字符串和列之间换算。

查询的代价取决于索引读到的行，与表的总行数关系不大。以类型开头的索引让每个查询只读到目标类型的行，所以键鼠事件再多，也不会拖慢一天只有几条的类型。Observation 不可改写（[OBSERVATION-15](../core/model/observation.mdx#observation-15)），表几乎只追加。

权威和投影分开，数据的正确性只取决于权威表：投影出错时可以丢弃重建，重建也不会改动权威数据。删除的身份必须是权威数据：已删除的 `observationId` 不能再分配（[OBSERVATION-12](../core/model/observation.mdx#observation-12)）。事物的类型只在 `things` 中，所以这一行是权威数据。事物只有身份，删除后保留这一行也不留下用户的内容。删除时间不影响任何规则，所以不保存，被删除的数据也少留一项痕迹，见 [ADR · 删除](./deletion.mdx)。

默认视图不保存结果，因为否定、替换和 Adoption 随时可能到来，范围否定还要对迟到的 Observation 生效。保存结果就要在每次写入时重算受影响的全部行。

命题键和状态键写成摘要，比较时不用读内容，也不用让 SQL 理解字段定义。

`observation_references` 带上角色，对象视图和删除事物都不用读内容就能归类。

个人数据的写入量不高。所有操作串行执行，检查和写入之间就不会插进别的操作，删除也不会和引用它的新 Observation 交错。一个请求一个事务，事务提交的次数从 Observation 数降到请求数，导入大量数据时差距最大。

PostgreSQL 的范围类型按重叠匹配，与 API 的时间查询规则一致，GiST 索引直接支持这种查询。

放弃的方案：

- **每个业务类型一张、按字段建列的表。** 每条修订都要改表，嵌套的引用放不进列。
- **按业务类型分区。** 可以按类型删除数据、统计空间，但后端要在运行时建表，按 id 读取还要先查一张身份表。分区对 API 和 Application 透明，需要时可以再改。
- **每份 Observation 一个事务。** 导入时事务提交的次数等于 Observation 数。
- **在 `content` 上建 GIN 索引，查询时匹配 id。** 索引不知道哪些位置是引用，会匹配到恰好等于某个 id 的普通字符串。
- **反查表每个引用位置一行。** 行数随引用位置增长，读取时省下的只是一页内的枚举。
- **保存默认视图的结果。** 一条范围否定可能改变几十万行。
- **事物另建一张删除表。** 事物只有身份和类型，多一张表没有好处。
- **墓碑保存识别依据的原文。** 依据里有路径、会话标识这样的来源信息，留下原文就是留下内容。

## 代价 [#costs]

- 所有类型共用一张表的统计信息和清理。按业务字段过滤时，索引要建成带类型条件的部分索引。
- `deleted_observations` 和 `key_tombstones` 永久占用空间。
- 写入串行执行，吞吐受单个事务的速度限制。
- 保存和删除时，七张投影要在同一个事务中同步更新。
- 默认视图在每次查询时计算，复杂度比按列筛选高。数据量上去之后可能要加物化的结果，这件事没有测过。
- 列出引用方时，每一页都要重新解析引用方的内容。
- 反查表的正确性依赖保存时对 SchemaRevision 的解析，解析规则改变时要重建投影。
- 子串扫描随数据量线性增长。
