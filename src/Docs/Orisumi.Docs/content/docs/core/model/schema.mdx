---
title: "Schema"
description: "一种 Observation 类型，以及它每次修改的字段、约束与含义"
---

Schema 定义一种 Observation 类型，例如“前台时段”，身份是 SchemaId。每次修改是一条 SchemaRevision，身份是 `schemaRevisionId`，内容是这种类型这一次的字段、约束和含义。

每份 Observation 都引用它保存时所用的 SchemaRevision。类型后来增减了字段，旧数据仍按当时的 SchemaRevision 解释，不需要迁移。两台设备可以各用各的修订，所以一种类型可以同时有多条修订在使用。

事物的类型和 Observation 的类型分开声明，见[事物类型](#thing-types)。

<ModelRelations node="Schema" />

- **身份**：SchemaId 是业务类型的常量；`schemaRevisionId` 由后端生成
- **被引用**：Observation 的 `schemaRevisionId`，事物的 `schemaId`
- **决策**：[ADR · 事物与观测](../../adr/things-and-observations.mdx)、[ADR · 不可变的 Observation](../../adr/immutable-observations.mdx)

## 字段 [#fields]

SchemaRevision 的内容：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `displayName` | 非空字符串 | 类型名称，见 [SCHEMA-4](#schema-4) |
| `description` | 非空字符串 | 业务说明，见 [SCHEMA-4](#schema-4) |
| `resourceName` | 字符串 | 类型的资源名，见 [SCHEMA-5](#schema-5) |
| `stateFields` | 字段名的数组，可选 | 声明后这个类型是状态，见 [SCHEMA-20](#schema-20) |
| `claimFields` | 字段名的数组，可选 | 这些字段的值和类型构成命题键，见 [SCHEMA-21](#schema-21) |
| `fields` | 字段名到字段定义的映射 | Observation 的业务字段，引用也是字段 |

## 字段定义 [#field-definitions]

| 配置 | 适用的字段 | 含义 |
| --- | --- | --- |
| `type` | 所有字段 | 值的类型 |
| `description` | 所有字段 | 非空字符串，说明字段或数组元素的业务含义 |
| `required` | 所有字段，数组元素除外 | 字段是否必须出现 |
| `nullable` | 所有字段 | 字段出现时，值能否为 `null` |
| `fields` | `object` | 对象的成员，结构与顶层 `fields` 相同 |
| `items` | `array` | 数组元素的字段定义 |
| `target` | `reference` | 引用的目标：`thing` 是事物，`observation` 是 Observation |
| `role` | 目标为事物的 `reference` | 这个字段和被引用事物的关系，见 [SCHEMA-19](#schema-19) |
| `searchable` | `string` | 布尔值，可选。声明后搜索读这个字段，见 [SCHEMA-22](#schema-22) |

| `type` | 值 |
| --- | --- |
| `string` | 字符串 |
| `boolean` | 布尔值 |
| `integer` | 整数 |
| `number` | 数值，可以包含小数 |
| `reference` | 目标事物的 `thingId`，或目标 Observation 的 `observationId`，由 `target` 决定 |
| `binary` | 二进制内容的描述，见 [Binary](./binary.mdx) |
| `object` | JSON 对象 |
| `array` | JSON 数组 |

## 示例 [#example]

下面的业务类型是状态，每个相关事物一份，有三个字段：`title` 必须出现，可以为 `null`，搜索读它；`relatedId` 引用一个事物，这条陈述是关于它的；`identifiers` 是对象数组，每个元素的 `sourceId` 引用一份 Observation。

```json
{
	"displayName": "示例条目",
	"description": "一个带标题、事物引用和平台标识线索的示例条目。",
	"resourceName": "example-items",
	"stateFields": ["relatedId"],
	"fields": {
		"title": {
			"type": "string",
			"description": "条目的标题；未取得标题时为 null。",
			"required": true,
			"nullable": true,
			"searchable": true
		},
		"relatedId": {
			"type": "reference",
			"target": "thing",
			"role": "about",
			"description": "与这个条目相关的事物。",
			"required": true,
			"nullable": false
		},
		"identifiers": {
			"type": "array",
			"description": "来源提供的平台标识线索；没有线索时为空数组。",
			"required": true,
			"nullable": false,
			"items": {
				"type": "object",
				"description": "一项平台标识线索，以及提供它的 Observation。",
				"nullable": false,
				"fields": {
					"scheme": {
						"type": "string",
						"description": "标识线索的种类，决定 value 的解释方式。",
						"required": true,
						"nullable": false
					},
					"value": {
						"type": "string",
						"description": "来源提供的标识原值，保留原文。",
						"required": true,
						"nullable": false
					},
					"sourceId": {
						"type": "reference",
						"target": "observation",
						"description": "提供这项线索的 Observation；来源没有保存为 Observation 时省略。",
						"required": false,
						"nullable": false
					}
				}
			}
		}
	}
}
```

## 类型与修订 [#types]

### SCHEMA-1 一个 Schema 一种类型 [#schema-1]

定义

一个 Schema 定义一种 Observation 类型，每次修改是它的一条 SchemaRevision。同一类型的 Observation 共用一个 SchemaId，各有自己的 `observationId`。修订之间没有先后之外的关系，也没有当前修订：写入方用它声明的那一条。

### SCHEMA-2 按 SchemaRevision 解释 [#schema-2]

执行方：后端、读取方

Observation 按它引用的 SchemaRevision 校验和解释：有哪些字段、哪些位置是引用、每个字段是什么含义，都由这条修订决定。新的修订只作用于引用它的 Observation，已保存的 Observation 继续按原来引用的修订解释。

### SCHEMA-3 只按声明校验 [#schema-3]

执行方：后端

后端只按已声明的 Schema 校验业务数据。Observation 引用的 SchemaRevision 必须已保存，事物的类型必须已声明。

### SCHEMA-4 名称与说明 [#schema-4]

执行方：写入方、后端

`displayName` 和 `description` 必须是非空字符串，后端检查这一点。`description` 还必须说明这种类型记下的业务事实、粒度和事实时间的取值，由写入方负责，人和 Agent 都靠它理解数据。

## 资源名与字段名 [#names]

### SCHEMA-5 resourceName 唯一 [#schema-5]

执行方：后端

`resourceName` 属于业务类型：同一个 Schema 的各修订使用相同的 `resourceName`，不同的业务类型不得使用相同的 `resourceName`，事物类型和 Schema 共用这一个范围。Schema 删除后，它的 `resourceName` 可以由新的业务类型使用。它用于发现和访问一种类型，用法见 [API](../../api/index.mdx) 和 [Storage](../../storage/index.mdx)。

### SCHEMA-6 resourceName 格式 [#schema-6]

执行方：后端

`resourceName` 只使用小写字母、数字和连字符，并以字母开头，例如 `local-applications`。

### SCHEMA-7 不用 id 字段 [#schema-7]

执行方：后端

顶层字段不得命名为 `id`。Observation 的身份由[它的成员](./observation.mdx#members)提供。

### SCHEMA-8 引用字段的名字 [#schema-8]

执行方：写入方

`reference` 字段的名字以 `Id` 结尾，元素是这种引用的数组以 `Ids` 结尾，目标是事物和 Observation 都一样。对象成员也一样。名字的前半部分写目标在这里的角色，例如前台应用时段引用本机应用的 `localApplicationId`，复核引用被复核的 Observation 的 `targetId`。

## 字段约束 [#constraints]

### SCHEMA-9 reference [#schema-9]

执行方：后端

`reference` 必须声明 `target`，非空值必须是对应的 `thingId` 或 `observationId`。顶层字段、对象成员和数组元素都可以是 `reference`。

### SCHEMA-10 字段定义必写项 [#schema-10]

执行方：写入方、后端

每个字段定义必须写明 `type`、`description`、`required` 和 `nullable`，这些配置没有默认值。数组元素写 `type`、`description` 和 `nullable`，不写 `required`。对象的每个成员也遵守这条规则。

`description` 必须是非空且不全为空白的字符串，由后端检查；它描述字段或数组元素本身，业务值允许为 `null` 不影响说明的必填要求。

写入方用 `description` 说明字段或数组元素的业务含义，以及适用的单位、取值解释、来源、引用目标与角色、省略和 `null` 的含义。读者应能结合所属类型的说明理解数据，不依赖形成数据的程序。

### SCHEMA-11 required 与 nullable [#schema-11]

执行方：后端

`required` 和 `nullable` 分别判断：`required` 决定字段能否省略，`nullable` 决定字段出现时能否为 `null`。

| `required` | `nullable` | 省略字段 | 值为 `null` | 类型匹配的非空值 |
| --- | --- | --- | --- | --- |
| `true` | `false` | 不允许 | 不允许 | 允许 |
| `true` | `true` | 不允许 | 允许 | 允许 |
| `false` | `false` | 允许 | 不允许 | 允许 |
| `false` | `true` | 允许 | 允许 | 允许 |

### SCHEMA-12 只收已声明字段 [#schema-12]

执行方：后端

Observation 只接受已声明的字段，对象成员也一样。字段定义只接受[字段定义](#field-definitions)中列出的配置。

### SCHEMA-13 省略与 null [#schema-13]

执行方：后端

“省略”和“值为 `null`”是两种状态：省略的字段读回时不出现，值为 `null` 的字段读回时是 `null`。

### SCHEMA-14 对象与数组 [#schema-14]

执行方：后端

对象用 `fields` 声明成员，数组用 `items` 声明元素；只有 `object` 有 `fields`，只有 `array` 有 `items`。数组的约束分层生效：

| 配置 | 约束什么 |
| --- | --- |
| 数组字段的 `required` | 数组字段能否省略 |
| 数组字段的 `nullable` | 数组本身能否为 `null` |
| `items.nullable` | 数组元素能否为 `null` |
| `items.fields` 中成员的配置 | 每个对象元素的成员 |

## 类型的演进 [#changes]

### SCHEMA-15 结构变了，出新修订 [#schema-15]

执行方：写入方

结构或约束改变时，形成同一个 Schema 的新修订。增删字段、调整约束、改写 `displayName` 或 `description` 的措辞，都属于这种情况；SchemaId 和 `resourceName` 保持不变。

### SCHEMA-16 含义变了，建新类型 [#schema-16]

执行方：写入方

业务含义改变时，必须新建一个 Schema，使用新的 SchemaId 和 `resourceName`。字段改名或改写 `description` 不得改变旧数据的含义。

## 事物类型 [#thing-types]

事物类型定义一种事物，例如“设备”。它和 Schema 分开声明，只有 `displayName`、`description` 和 `resourceName`，身份也是 SchemaId。

### SCHEMA-17 事物类型 [#schema-17]

执行方：后端

事物类型没有字段和修订，每个事物用 `schemaId` 引用它。再次声明同一个事物类型时，内容不同，后端保存最后一次的内容。

## 类型的声明 [#declarations]

这些声明让后端和读取方理解一种类型，所以默认视图、对象视图、搜索和删除都不用认识具体的业务类型。

### SCHEMA-19 引用的角色 [#schema-19]

执行方：写入方、后端

目标是事物的 `reference` 字段必须声明 `role`，说明这份 Observation 和被引用的事物是什么关系：

| `role` | 含义 | 例子 |
| --- | --- | --- |
| `about` | 这句话关于它 | Name 的 `thingId` |
| `part` | 这份 Observation 是它的一部分 | 助手交互的 `sessionId` |
| `mention` | 这句话提到它 | 助手交互的 `deviceId` |

对象视图按角色归类，见 [API · 对象视图](../../api/reading.mdx#thing-view)；删除事物时按角色决定移除什么，见 [HISTORY-10](../rules/history.mdx#history-10)。

### SCHEMA-20 状态 [#schema-20]

执行方：写入方、后端

`stateFields` 是可选的顶层字段名数组。声明后这个类型是状态，这些字段的值相同的 Observation 是对同一状态的不同说法。例如 Name 的 `stateFields` 是 `thingId`，一个事物同时有来源记下的名字、模型判断的名字和用户写的名字。默认视图在同一状态下取一条：用户写的优先，其次保存时间最晚的，见 [UNDERSTANDING-4](../rules/understanding.mdx#understanding-4)。

### SCHEMA-21 命题键 [#schema-21]

执行方：写入方、后端

`claimFields` 是可选的顶层字段名数组。类型加这些字段的值构成命题键，命题键相同的 Observation 说的是同一件事。例如线索归属是 `identifierId`、`productId`，Name 是 `thingId`、`name`。否定落在命题上，见 [REVIEW-4](./review.mdx#review-4)。

### SCHEMA-22 可搜索 [#schema-22]

执行方：写入方、后端

字符串字段可以声明 `searchable` 为 `true`，搜索只读这些字段，见 [API · 搜索](../../api/reading.mdx#search)。声明人和模型写下的文字，工具输出、注入的上下文这类材料不声明，例如[助手交互](../../observers/assistant-sessions/assistant-interaction.mdx)的工具输出。
