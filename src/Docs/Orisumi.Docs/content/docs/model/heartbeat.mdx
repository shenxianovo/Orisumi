旧 Heartbeat 已留下前台、浏览器、键鼠和 VRChat 等历史。例如，一天样本有 3,435 个时段、65,768 个事件和 642 个缺口；先按本人范围取得这些行及其关联，把数据库交付的原生表示留下，再从 Orisumi 原件恢复到一个空数据库，核对字段与关系。

当前已完成一次本人完整历史导出，包含3,748,506行，经既有[文件采集](./file-capture.mdx)保存，并在禁止读取原导出目录和使用 IP 网络的条件下独立恢复。格式及范围由 Agent 在自主授权下采用，依据是实际一天样本和文本往返验证，取舍见[原生文本决定](./adr/0007-native-postgresql-export.mdx)，完整历史的计数与成本见[验收](./validation.mdx#旧-heartbeat-完整历史)。

依据：

- [各处原样都存](../requirements/belief.mdx#各处原样都存)、[留最原始的一层](../requirements/belief.mdx#留最原始的一层)：取得旧库现存行值和模式，后续解释保留为独立步骤。
- [数据比代码长寿](../requirements/belief.mdx#数据比代码长寿)：恢复依靠保存的数据库原生格式与模式。
- [给别人看要隔离](../requirements/belief.mdx#给别人看要隔离)：旧库有多个所有者，本轮只取得明确的本人范围及必要共享关联。

## 行的范围

本人标识来自已有明确证据，开始时核对 `Users` 唯一匹配。各表按显式列清单保存完整行；发现新增字段或类型变化时，先保留模式差异并重审取得条件。

| 表 | 保存范围 |
| --- | --- |
| `Users` | 本人一行 |
| `Devices`、`Subjects`、`Streams` | 各表全部本人行，包括尚无事实引用的记录 |
| `Segments`、`Events`、`FactGaps` | 全部本人现存历史，保留原起止值和所有字段 |
| `AppIdentities` | 上述时段、事件和设备实际引用的非空身份 |
| `Apps` | 所选应用身份实际引用的应用 |
| `__EFMigrationsHistory` | 当前迁移记录，作为模式证据 |

事实到流、流到主体、主体到设备及应用关联分别核对。关联缺失或指向其他所有者时记录缺口，当前本人范围保持明确。

全历史没有日期过滤，因此取得缺口表的 `bigint` 原整数无需先解释其时间单位。已有勘探将其解释为 .NET ticks，所有旧写入方是否使用 UTC 仍需额外证据。归档保留现存行版本；来源已经删除的行和历史中间修订属于尚不可得的材料。已有理解、图标等其他表按各自来源价值另行勘探。

## 一份一致导出

在一个连接的 `REPEATABLE READ READ ONLY` 事务中，先对选定表取得 ACCESS SHARE 锁，再读取模式和数据，最后结束事务。实际 SQL、对应交互的发送与接收时间、原始输出与诊断分别保存；每表前后及事务末记录服务器时刻、事务快照、隔离级别和只读状态。交互区间和服务器观察时刻各自保留，全部关联都对应这次快照中的当前行。

每表使用 `COPY (SELECT ...) TO STDOUT WITH (FORMAT text, ENCODING 'UTF8')`，按明确列顺序和稳定行排序取得。保留输出原字节；TAB 分列、`\N` 表示 SQL NULL，换行和反斜杠由数据库转义。准确列类型、顺序、可空性和约束原定义随模式证据保存。会话固定并记录 `DateStyle=ISO,YMD`、`TimeZone=UTC` 和 `client_encoding=UTF8`，另记录来源版本与服务器编码。[PostgreSQL COPY 格式](https://www.postgresql.org/docs/18/sql-copy.html#SQL-COPY-NOTES)

`jsonb` 的值已经经过来源数据库规范化，`timestamptz` 保存时间点；输入时的 JSON 排版与原时区名只能以来源当前实际保留的内容为准。当前已确认的列类型为整数、UUID、布尔、文本、时间点和 JSONB；新增类型先单独核对其原生表示与恢复条件。

取得失败或取消时，已经返回的字节和诊断保留，整轮明确为未完成。语句时间上限按实际成本设置并记录。一天样本的耗时仅描述该次读取，全历史另外计量。

## 保存目录与两次取得

导出目录包含 `rows/` 下每表原生 COPY、`source/` 下实际查询和完整出处、模式原输出，以及导出完成状态和文件摘要。`restore/` 中提供从模式生成的恢复 SQL，注明它是派生的便利材料；来源模式原文继续保留。

全部表和事务末尾证据取得后，冻结这个目录，再交给文件采集：

```sh
orisumi run capture files <完整导出目录> --once --store <原件存储目录>
orisumi run raw restore <采集根> <新的恢复目录> --store <原件存储目录>
```

采集根沿用 `source=files`，`origin` 是实际导出目录的本机绝对路径，根的内容哈希表示这次保存。真正的数据库位置、本人标识、原事务时刻、命令与取得条件位于保存的元信息中。文件取得和数据库导出有各自的时间与出处，后续使用按这两层事实追溯。

文件采集成功证明目录字节已经保存；数据库导出是否完整，还要看目录里的状态和关联核对证据。

## 恢复验收

先从原件恢复全部文件并核对长度与哈希，再只使用恢复目录，在专用 PostgreSQL 空库中重建准确列类型，导入表值，依次恢复主键、检查约束与外键。按保存的列顺序、排序和会话设置重新导出，逐表比较全部字节，同时核对行数、NULL 和关系。

一天样本在来源 PostgreSQL 18.4 与本机 18.6 间完成往返，10 表共 69,972 行、74 个约束通过。文本导出 19,225,157 字节，比来源二进制表示多 20.27%；文本导入后再导出的二进制与最初来源字节完全相同。不同主版本和新字段类型需要各自验证。

当前先保住这处遗留来源的现存历史。后续若确认仍持续产生需要保留的新材料，再按变化速度与整轮成本决定持续取得方式。
