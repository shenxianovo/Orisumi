2026-11-06 的验证覆盖了分块方式对照、Codex 原件取得与异机恢复，以及 macOS 前台观测的实际应用切换、保存和停止。例如，保存一轮 Codex 材料后，只给异机读者完整保存集；恢复出的数据库可以独立打开，日志和附件按清单核对字节，来源目录中的后续变化不参与这次核对。

本页公开测量方法、聚合结果、限制和仓库中的复现入口。真实来源样本、原始采集、逐文件清单与完整实验输出保留在本机，不随公开仓库提供。下面的数字描述这次样本；使用其他样本重跑，应重新记录结果。

## 整文件与分块对照

比较整文件复用、固定 1 MiB 块和当前 `orisumi-cdc-1`。三种方式都按 SHA-256 复用相同内容，再统一用 Python 3.14 的 `compression.zstd`、level 3 编码；压缩后更大时保留原文，zstd 魔数开头的原文按[块编码规则](./raw.mdx#块)处理。

下表采用十进制 MB，即 1 MB = 1,000,000 字节，只计去重后再压缩的内容体积。采集记录、清单和文件系统开销另算。

| 输入与范围 | 整文件复用 | 固定 1 MiB 块 | 当前 CDC |
| --- | ---: | ---: | ---: |
| 真实静态集：1,271 个文件、586.507 MB | 127.222 MB | 154.180 MB | 149.032 MB |
| 大日志的 10 个不同字节前缀版本，最终 33.434 MB | 55.586 MB | 17.284 MB | 16.323 MB |
| 小日志的 10 个不同字节前缀版本，最终 0.181 MB | 0.303 MB | 0.303 MB | 0.303 MB |
| 大日志每个前缀重新 zstd 压缩，10 个不同版本 | 54.647 MB | 22.027 MB | 26.644 MB |
| 大日志中部逐次插入合成行，10 个不同版本 | 102.466 MB | 82.143 MB | 17.063 MB |

静态集来自已经停止写入的一份 Claude Code 保存内容，两次采集的清单相同，第二次在三种方式下新增内容均为零。其余四组使用静态集中的日志字节构造变化，代表受控回放。大日志为 33,433,988 字节，小日志为 181,421 字节。字节前缀按最终长度的十分之一递增，允许末行不完整；中部插入组逐次增加一行明确标记的合成内容。每组第 11 轮重复第 10 轮，三种方式的新增内容对象和字节均为零。

### 去重与压缩

| 输入 | 整文件：唯一原文字节 | 固定块：唯一原文字节 | CDC：唯一原文字节 |
| --- | ---: | ---: | ---: |
| 静态集 | 586,491,383 | 583,345,655 | 585,163,655 |
| 大日志前缀 | 183,886,930 | 38,134,866 | 38,377,876 |
| 小日志前缀 | 997,811 | 997,811 | 997,811 |
| 重压缩前缀 | 55,585,773 | 22,031,341 | 26,643,106 |
| 中部插入 | 334,342,400 | 183,347,456 | 37,720,985 |

静态集的大部分缩小来自压缩，CDC 仅复用了约 1.343 MB 原文。整文件有更长的压缩上下文，这组压缩后比 CDC 少约 21.810 MB。大日志前缀的 CDC 唯一原文总量比最终文件多 4,943,888 字节：已经封闭的前部块可以复用，变化的尾块仍需重新保存。

小于 256 KiB 的完整内容在当前切块器中是单块，因此小日志组与整文件相同。固定块在追加前缀组表现接近 CDC；中部插入导致后续固定边界偏移，这一组 CDC 复用更多。重新压缩的组中仍存在相同字节区段，固定块优于当前 CDC；其他压缩器、帧结构、字典和内容需要分别测量。

### 验证与复现

CDC 边界直接取自当前 C# 采集器的清单：最小 256 KiB、平均 1 MiB、最大 4 MiB，归一化级别 2。每个块核对 SHA-256，清单核对完整哈希，各轮文件拼接后核对长度、完整哈希，并与当轮输入逐字节比较。独立 Python 读者按[保存格式](./raw.mdx)解码原件，未调用 Orisumi 的读取接口。

公开代码中的 `tests/Orisumi.Raw.Tests/ChunkerTests.cs`、`BlockStoreTests.cs` 和 `RawStoreTests.cs` 分别覆盖切块、块编码校验和重复取得的行为。按改动运行这些检查使用 `orisumi verify`。

用自己的样本重复对照时，先固定一份输入，再生成严格不同的前缀、重新压缩版本和中部插入版本。每个版本用相同实验存储取得：

```sh
orisumi run capture files <本轮样本目录> --store <实验存储目录> --once
orisumi run raw list --store <实验存储目录>
orisumi run raw show <采集记录> --store <实验存储目录>
orisumi run raw restore <采集记录> <新的恢复目录> --store <实验存储目录>
```

从清单取实际 CDC 块；另将同一输入按整文件和固定 1 MiB 切分。分别按原文字节的 SHA-256 去重，再用同一编码器计算内容体积。把压缩前唯一字节与压缩后字节分列，保留各轮结果，最后重复上一版检查新增量。

这次静态 CDC 内容文件占 149,032,273 字节，文件系统分配 152,494,080 字节；另有两个采集根共 736 字节、一个清单块 95,591 字节。回放有 11 个采集根共 4,021 字节、10 个清单块共 16,887 字节。整文件与固定块方案的等价元数据尚未实现，完整存储成本比较仍需补测。

当前证据覆盖静态样本和受控变化。真实连续历史、CPU、内存、写入耗时、网络流量、不同硬盘、小文件打包和其他来源的体量尚待各自测量。

## Codex 取得与恢复

对本机 Codex 数据执行一次实际采集后，从隔离的 Orisumi 原件库恢复全部材料，再用独立 Python 程序逐项复核：

| 项目 | 结果 |
| --- | --- |
| 采集材料 | 1,981 个普通文件、142 个符号链接，共 1,602,517,392 字节；本轮没有缺项报告 |
| 取得方式 | 1,980 项文件原字节、1 项 SQLite online backup 整库快照、142 项链接目标字符串 |
| 内容核对 | 全部恢复文件的长度与 SHA-256、清单完整 SHA-256、全部链接目标字符串一致 |
| 数据库 | 恢复库有 17 张表，`PRAGMA quick_check` 返回 `ok` |
| 单文件导出 | 导出索引与整轮恢复得到的索引逐字节一致 |
| 部分失败 | 人工来源缺少索引与数据库时，唯一可读日志仍保留；采集记录列出缺项，`--once` 返回 1 |

每个普通文件对应读取时取得的字节，数据库是一份独立一致快照。日志、索引、附件与数据库分别取得，各自时间处于本轮采集窗口内；恢复核对保存清单。未知字段、原始压缩字节与附件均按取得内容保存。


先保留本轮清单，再让测试来源不可用，只从原件存储恢复。按[恢复格式](./raw.mdx#恢复与导出)检查每个文件的长度、完整哈希及链接目标；用 SQLite 打开恢复的数据库执行 `PRAGMA quick_check`。来源正在变化时，保存内容与后来源文件的差异按取得时间解释。

`tests/Orisumi.Capturing.Tests/CodexSourceTests.cs`、`SqliteSnapshotReaderTests.cs`、`CollectorTests.cs` 和 `tests/Orisumi.Raw.Tests/CaptureRecoveryTests.cs` 提供确定性样例，覆盖来源变化和消失、SQLite WAL 已提交内容、并发写入的表间一致性、部分失败、取消清理与恢复路径。实际来源的聚合结果和这些可重复样例分别提供证据。

Windows 实机、长期常驻与断电耐久性仍需各自验证；SQLite backup 调用的取消响应发生在调用前后。

独立读者使用 Python 3.12 与远端已有的 libzstd，未使用 Orisumi 程序。来源 `origin` 只作为元信息解释，不用于打开文件。访问范围结论来自读者代码与 Python 运行审计，实际数据始终在用户控制的位置。

另外用实际采集器生成三份合成历史、一份删除事实，并验证以下行为：

- 固定记录先复制，复制内容的 16.02 秒内完成第三版采集；副本保留选入的前两版且内容完整，第三版留给下一份副本。
- 内容先复制、新根随后生成、最后再复制记录的确定性交错会产生缺块，验证器指出具体块。
- 新完整副本有 3 份采集根、1 份删除事实、9 个块；2 份历史正常可见。旧副本合并最新可得事实后，已删除取得保持不可见。
- 将合成源库改名使原路径不可用，产品从副本恢复两份有效历史，字节和链接目标一致。真实 Linux 独立恢复与这一合成源不可用测试分别提供证据。
- 只在派生副本中制造缺块与损坏；产品恢复返回 1，定位块，未发布最终目录，也没有遗留恢复临时目录。

复制顺序依赖当前不可变对象、先内容后根及无物理回收的契约。第一阶段选入的记录集合可以跨多个时刻；备份完成时间不代表全库事务时刻。单独恢复较旧副本也无法得知后来才发生的删除，应合并最新可得删除事实。

复查自己的副本时，按[复制顺序](./nodes.mdx#同步)得到一个新目录，再从该目录列举、恢复与核对：

```sh
orisumi run raw list --store <副本目录>
orisumi run raw restore <采集记录> <新的恢复目录> --store <副本目录>
```

## 前台观测

macOS 前台入口已按[观察格式](./foreground.mdx)实现。在本机 macOS 27.0 上创建三个仅用于验证的 AppKit 应用 A、B、C，通过产品入口持续观察，独立记录激活请求、各应用自身的激活与失活回调、窗口成为 key window 的回调及标题修改。实际完成回调用来确认动作发生，激活请求返回成功本身不作为完成证据。

| 受控动作 | 应用侧证据 | Orisumi 观察结果 |
| --- | --- | --- |
| 约 1 秒间隔切换 | 7 次激活完成；请求间隔 1,001–1,038 毫秒 | 7 次对应激活通知全部取得 |
| 约 0.2 秒间隔切换 | 15 次激活完成；请求间隔 201–203 毫秒 | 15 次对应激活通知全部取得 |
| 同应用切窗与改标题 | 4 次窗口成为 key window，1 次标题修改 | 该阶段没有新增应用级通知 |
| 测试应用的激活与失活 | 各 22 次回调 | 各 22 次通知；PID、次数、按类别的顺序及每个应用内部顺序相符 |

整轮 49 条观察共 46,150 字节：1 条 `started`、1 条初始 `snapshot`、46 条通知及 1 条 `stopped`。通知包含测试应用的 44 条及原前台应用的失活、恢复激活两条。序号连续 1–49，采集根均无失败。49 份原件逐份通过 `orisumi run raw restore` 恢复，再独立核对 SHA-256、长度、LF、来源、取得方式、运行身份与序号，全部通过。结束时恢复原前台应用并退出三个测试应用。

### 通知顺序的含义

22 次切换中，workspace 都先交付新应用激活，再交付旧应用失活；21 次发生在测试应用之间的切换，其应用自身回调则先失活、后激活。helper 的激活回调比应用自身的激活完成回调早 5–23 毫秒。这符合 Apple 对 [workspace 激活通知](https://developer.apple.com/documentation/appkit/nsworkspace/didactivateapplicationnotification)的“即将激活”语义。

因此两条通道按类别和单应用核对，保留各自真实交付顺序。`observedAt` 与 `sequence` 表达取得时刻与输出顺序；以后解释活动时段时，需要结合通知含义，不能把跨通道交错直接当成统一的源端时间线。应用动态属性还受 [NSRunningApplication 的 run loop 缓存](https://developer.apple.com/documentation/appkit/nsrunningapplication)影响。

### 生命周期与故障

有限时长运行和重启得到不同的运行身份；每轮留下 `started`、初始 `snapshot` 和 `stopped`，通过产品恢复命令取回。`started` 在注册订阅之前输出，代表程序启动事实；订阅前的切换与未运行期间的活动保持未知。

真实终端 Ctrl+C 曾暴露开发入口提前终止进程树的问题。修复后先等待两条观测已经存入，再发送 Ctrl+C；命令返回 130，三条完整观测均可恢复，最后一条为 `stopped`、`reason: stop-requested`，采集根均无失败。修复前强制终止留下的两条前缀也仍可读回。

9 项前台行为测试覆盖：进程存活期间的即时读回、取消后保存结束行、非零退出与 stderr、半行原字节保留、乱序协议行、缺失结束事实、停止超时回收、存储失败、有效待存行回存后的路径与计数，以及原生 helper 接到 SIGINT 后等待父进程正常停止。开发工具的真实子进程回归另外验证有界等待期间保留末尾输出，以及超时后结束进程。

### 网络限制与重启

进程级实验先验证策略：IPv4 与 IPv6 的 TCP、UDP 连接、发送及绑定均被拒绝并返回 `EPERM`；自建 UNIX stream 连接仍可用。此前的 `(deny network*)` 连本机 UNIX socket 一并禁止，使开发入口停在 SDK restore 的项目图发现阶段。按本轮问题改为拒绝全部 IP 入站、出站与 bind，保留本机 IPC 后，相同 `orisumi run` 入口正常运行；未修改生产采集代码。

同一限制策略下完成两轮实际前台观察，各保存 19、21 条：

| 项目 | 结果 |
| --- | --- |
| 原件恢复 | 40/40 份、37,586 字节，记录、清单和原件的 SHA-256 与长度均通过核对 |

## 并发发布

三个采集进程开始共用同一原件目录前，先用三个独立写进程和一个独立恢复进程验证。旧的发布方式在并发保存相同内容时，会让多个写者同时报告 `Added=true`；最小回归明确得到“期望 1，实际 2”。现有串行去重测试没有覆盖同时发布同一个键的情况。

当前 macOS/Linux 先写完并关闭同目录临时文件，再以 `link` 原子创建最终名字；已存在的目标保持原内容，只有实际创建者报告新增。Windows 沿已有移动接口处理明确的存在冲突。文件系统不支持这一原子发布能力时明确失败；原件格式、哈希与编码均保持原契约。根因与接口依据见 [.NET Unix 移动实现](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/IO/FileSystem.Unix.cs)及 [Apple link 契约](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/link.2.html)。

修复后在本机 macOS 重跑 20 个全新存储：40 次共享块或记录竞争，均恰好一个写者报告新增；60/60 份采集恢复成功，其中 40 次恢复时其他写者仍在运行。833 次枚举没有发现半成品，最终临时文件为零，四个进程均正常退出。新增回归另覆盖不同内容争用后的胜者保持、目录冲突及临时文件清理。Windows/Linux 写入与断电持久性未在本轮实机验证。

### 完整性与停止

真实 bundle 只保留头部、截去 pack 尾部，或将引用指向不存在对象时，空库 verify 仍可能返回 0。完整轮因此继续在新目录 mirror clone，再运行 fsck；截断包与悬空引用各有先失败再修复的回归，HEAD 单独悬空也由独立试验确认 clone 拒绝。

Git 父进程先退出而子进程仍持有输出管道时，初稿取消后仍一直等待。独立复现保留了这个失败；修复后取消约 2.034 秒返回，已经取得的二进制前缀逐字节保留，命令和采集结果记录管道缺口。已脱离父进程的后代仍可能存活，夹具显式清理自己的后代；活父进程树的取消另有回归。
