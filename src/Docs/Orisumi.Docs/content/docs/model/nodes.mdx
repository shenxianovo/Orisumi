当前副本路线采用外部完整备份：通过已有远程连接，用 `rsync` 将保存内容复制到用户控制的另一台机器，每次使用独立版本目录，在原目录不可用时恢复并核对。它承接[多处都有一份](../requirements/belief.mdx#多处都有一份)的目标。

例如，从测试存储的一份采集记录出发，备份它引用的清单和全部内容块，再从备份恢复到空目录。核对内容、出处和链接目标，才能证明这份副本能用。仅看到远端目录里有文件，还需要检查记录引用的内容是否齐全。

采用理由见 [0003 副本先验证外部备份](./adr/0003-mesh-with-full-nodes.mdx)，本机并发实验与异机验证的实际覆盖见[验收记录](./validation.mdx#外部副本)。当前按需执行，自动备份和保留期另按运行需要安排。

## 同步

当前复制顺序是先 `config.json` 和完整 `records/`，再 `blocks/`，排除 `.pending` 临时文件：

```sh
rsync -a --exclude='*.pending' <存储>/config.json <存储>/records <新工作目录>/
rsync -a --exclude='*.pending' <存储>/blocks <新工作目录>/
```

工作目录可以是远端路径。开始前建立仅本人可读的独立目录，校验全部记录、引用的块和恢复内容后，再将它改名为已验证版本。已有版本继续保留。

这个顺序依赖当前写入契约：内容块先写，根最后发布；已发布对象不可变；当前没有物理回收。第一阶段完成后，选入的记录集合固定，第二阶段能复制其已经存在的全部内容。之后写出的根留给下一版，第二阶段多带的未引用块可以保留。第一阶段枚举也可能跨越多个时刻，因此一份副本表示实际取得的记录集合。

反过来先复制内容再复制根，并发采集可能让新根指向尚未复制的块。以后引入物理回收或修改对象时，必须重审这一操作契约；必要时再增加固定保存集导出。应用内对象交换协议等外部路线暴露出具体问题时比较。

采集记录、清单、内容块和删除记录都是长期保存事实。恢复旧副本时，将后来已经取得的删除记录一起带回，才能保持当前已删除采集不可见。只有旧副本时，只能恢复它当时知道的删除事实。历史副本仍可能包含逻辑删除的字节，物理清理需要单独安排。

## 节点何时进入

实际出现跨设备查询，或外部备份无法满足的复制需求时，再评估由 Orisumi 提供节点能力。先比较单个常开入口是否足够；只有设备之间直接交换解决了真实问题，才评估网状拓扑。

到那时，先用两台实际设备完成一份保存内容的交换与恢复，核对断开、重连和缺块行为，再决定节点角色、交换进度和清理规则。完整节点、部分节点和各端统一接口都随这次验证具体选择。

若自己的设备需要直接连接，私有网络是待验证的起点：核对网络成员和凭据拥有者，验证非成员无法取得数据。给别人共享材料另按[给别人看要隔离](../requirements/belief.mdx#给别人看要隔离)确定内容与权限。

## 回收

当前删除写成记录，使目标采集从正常列举和查找中消失；物理块继续保留，见[删除记录](./raw.mdx#删除记录)。

用户提出物理删除或回收需要时，先列出目标、共享引用和可以释放的范围，再按获准范围执行。验收要同时覆盖保留采集的完整恢复与待回收内容的去向。当前保存链路先承担写入与恢复，空间回收后置。
