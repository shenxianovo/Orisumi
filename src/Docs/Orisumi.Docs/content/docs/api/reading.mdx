读取默认得到后端算好的默认视图，所有读取方共用。已删除的事物和 Observation 返回 `410`，读取方把它列为不可读取，见 [HISTORY-8](../core/rules/history.mdx#history-8)。

## 表示 [#representation]

Observation 的 JSON 成员就是 [Observation · 成员](../core/model/observation.mdx#members) 中列出的那些。写入时调用方给出内容、形成方式和事实时间，其余成员由后端形成，见 [Writing](./writing.mdx)。事物的表示见[事物](#things)，SchemaRevision 见[类型](#types)。

- Observation 的可空成员一定出现，没有值时为 `null`。
- `content` 就是业务字段组成的对象。

读回的内容与写入的值相同，写法可以不同：对象的键不保留原来的顺序，数字可以换成等值的写法，例如写入 `1e2`，读回 `100`。时间的写法见[时间](#time)。

API 字段使用 `camelCase`，对应 C# 的 `PascalCase` 和数据库的 `snake_case`，见 [Storage · 命名](../storage/index.mdx#naming)。

### 时间 [#time]

API 中的时间精确到 1 微秒，UTC 指协调世界时。事实时间的含义见 [Observation · 事实时间](../core/model/observation.mdx#fact-time)。

例如 VS Code 的时段从北京时间 14:00 开始：

- 写入 `2026-10-06T14:00:00+08:00`，读回 `2026-10-06T06:00:00Z`。
- 不足一微秒的尾数舍去：写入 `1999-12-31T23:59:59.9999999Z`，读回 `1999-12-31T23:59:59.999999Z`。截断的位置见 [PostgreSQL · 时间](../storage/postgresql.mdx#time)。

| 参与方 | 职责 |
| --- | --- |
| 写入方 | 写入事实时间，字符串以 `Z` 结尾或带明确的 UTC 偏移 |
| 后端 | 转换为 UTC，向下截断到整微秒后保存；读取时返回以 `Z` 结尾的字符串；保存每份 Observation 时赋值 `recordedAt` |
| 前端 | 按浏览器或系统时区显示时间 |

`timeZone` 非空时，必须是可解析的 IANA 时区 ID。时间或时区校验失败时返回 `400`。

`recordedAt` 一定存在，它是后端保存这份 Observation 的时刻，以 `Z` 结尾，精确到微秒，见 [OBSERVATION-16](../core/model/observation.mdx#observation-16)。

## 视图 [#view]

第二天用户否定了 15:00 到 16:00 的推断，读取方不用看 Review，后端已经算好。`view` 适用于查询观测、搜索和列出引用方：

| `view` | 结果 |
| --- | --- |
| `current`，默认 | 默认视图，规则见 [UNDERSTANDING-4](../core/rules/understanding.mdx#understanding-4) |
| `all` | 全部 Observation，包括被否定和被替换的 |

默认视图的结果带两个成员，有内容时才出现：

| 成员 | 含义 |
| --- | --- |
| `deniedRanges` | 这一条被部分否定时，被否定的时段，由读取方裁剪 |
| `basisDenied` | 它的 InputSet 中有被否定的陈述时为 `true`，这条陈述仍然显示，见 [UNDERSTANDING-8](../core/rules/understanding.mdx#understanding-8) |

例如那条“14:00 到 16:00 在写代码”的推断：

```json
{
  "observationId": "019e1bbb-ec00-7000-8000-000000000301",
  "deniedRanges": [
    { "startAt": "2026-10-06T07:00:00Z", "endAt": "2026-10-06T08:00:00Z" }
  ]
}
```

## Observation [#reads]

| 读取 | 接口 |
| --- | --- |
| 一份 | [`GET /observations/{observationId}`](/api/getObservation) |
| 一组 | [`POST /observations/read`](/api/readObservations)，一次 1 到 256 份 |
| InputSet 的成员 | [`GET /input-sets/{inputSetId}`](/api/getInputSet) |

按 id 读取得到这份 Observation 本身，不经过默认视图，所以追溯时读到的是当时的内容，被替换和被否定的也一样，见 [REFERENCE-1](../core/rules/references.mdx#reference-1)。

批量读取时，响应按请求的顺序逐项返回，请求中重复的项也各有一项：

| `status` | 含义 |
| --- | --- |
| `found` | 带着这份 Observation 的完整内容 |
| `not_found` | 这个身份从未出现过 |
| `deleted` | 已被删除，见 [HISTORY-8](../core/rules/history.mdx#history-8) |

## 内容 [#contents]

第二天 Web 控制台显示 VS Code 的时段，从时段的 `icon` 读到描述，再用 [`GET /contents/{digest}`](/api/getContent) 取得字节，按描述中的 `mediaType` 显示，见 [BINARY-5](../core/model/binary.mdx#binary-5)。

- 响应体是原始字节，`Content-Type` 为 `application/octet-stream`。
- 摘要确定了字节，所以响应带 `Cache-Control: private, max-age=31536000, immutable`，读取方可以按摘要长期缓存。
- 没有已保存的 Observation 使用这份内容时返回 `404`，包括使用它的 Observation 都已删除的情况。

## 类型 [#types]

[`GET /schema-revisions`](/api/listSchemaRevisions) 列出 Observation 类型的修订，`resourceName` 只返回这种类型的，[`GET /schema-revisions/{schemaRevisionId}`](/api/getSchemaRevision) 读取一条。[`GET /thing-types`](/api/listThingTypes) 列出事物类型。

## 事物 [#things]

[`GET /things`](/api/listThings) 列出事物，按 `thingId` 升序排列，`resourceName` 只返回这种类型的事物。[`POST /things/read`](/api/readThings) 一次读取 1 到 256 个事物，响应的 `status` 和[批量读取](#reads)相同。

每个事物带着它的类型、识别依据和名字。名字取自默认视图中这个事物的 [Name](../core/model/common-types.mdx#name)，所以显示一批设备或会话时一次请求就够。`nameObservationId` 是名字所在的 Name，读取方读它就知道这个名字是谁写的、怎样形成的，例如前台状态 Observer 直接记下，或者会话理解 Observer 推断。

## 对象视图 [#thing-view]

用户打开 VS Code 这个本机应用。[`GET /things/{thingId}`](/api/getThing) 返回它现在的样子、它的关系和发生过的事：

```json
{
  "thing": {
    "thingId": "01a12e31-9050-7000-8000-000000000101",
    "schemaId": "019e1bbb-ec00-7000-8000-000000000002",
    "keys": [],
    "name": "Visual Studio Code",
    "nameObservationId": "01a12e31-9050-7000-8000-000000000130"
  },
  "sameAsThingIds": [],
  "state": [],
  "relations": [],
  "activity": [
    {
      "resourceName": "foreground-application-periods",
      "role": "part",
      "count": 1824,
      "href": "/observations?thingId=01a12e31-9050-7000-8000-000000000101&role=part&resourceName=foreground-application-periods"
    }
  ]
}
```

| 成员 | 内容 | 选取 |
| --- | --- | --- |
| `thing` | 事物和名字 | 见[事物](#things) |
| `sameAsThingIds` | 按 Same-As 和它是同一个的事物 | 见 [SAMEAS-3](../core/model/same-as.mdx#sameas-3) |
| `state` | 现在的样子 | 以 `about` 引用它，并且没有以 `about` 引用其他事物的 Observation |
| `relations` | 关系 | 以 `about` 引用它，同时以 `about` 引用其他事物的 Observation |
| `activity` | 发生过的事的计数和分页入口 | 以 `part` 或 `mention` 引用它的 Observation，按类型和角色各一项 |

全部按默认视图计算，并按成立的 Same-As 展开。`href` 是列出这一项的[查询](#observations)。角色的含义见 [SCHEMA-19](../core/model/schema.mdx#schema-19)。

## 查询观测 [#observations]

晚上，推断 Observer 用 [`GET /observations`](/api/listObservations) 读取当天的前台时段，内容就在结果中。条件都可以省略，给出的条件一起生效：

| 参数 | 只返回 |
| --- | --- |
| `from`、`to` | 事实时间与范围 `[from, to)` 相交的。两者同时给出或同时省略 |
| `thingId` | 业务字段引用这个事物的，按成立的 Same-As 展开 |
| `role` | 和 `thingId` 一起使用，以这个角色引用它的 |
| `observerId` | 由这个事物负责的 |
| `speakerId` | 这个事物说的。`speakerId` 为 `null` 的 Observation 按 `observerId` 比较，见 [OBSERVATION-20](../core/model/observation.mdx#observation-20) |
| `excludeSpeakerType` | 排除说话人是这种事物类型的，值是资源名。例如 `models` 排除模型的话 |
| `resourceName` | 这种业务类型的 |
| `formation` | 这种[形成方式](../core/model/observation.mdx#formation)的 |
| `view` | 见[视图](#view) |

`observerId` 指向的事物已删除时照常返回。不同 Observer 可以各有一份 Observation，见 [OBSERVATION-3](../core/model/observation.mdx#observation-3)。

给出 `from` 和 `to` 时，匹配只看已知的边界：

| 已知的边界 | 返回的条件 |
| --- | --- |
| 两个都已知 | 时段 `[startAt, endAt)` 与范围有重叠；时间点 `t` 满足 `from ≤ t < to` |
| 只知道一个 | 把这个边界当作时间点 `t`，满足 `from ≤ t < to` |
| 两个都未知 | 不返回 |

省略时间范围时，两个边界都未知的 Observation 也返回。

结果按已知的开始边界排序，开始边界未知时用结束边界，`order` 为 `asc`（默认）或 `desc`；相同时按 `observationId` 升序。两个边界都未知的排在最后，两种顺序都一样。

## 搜索 [#search]

模型回答“十月在纠结什么”时，先用 [`GET /search`](/api/searchObservations) 找出相关的原文。第一版是子串扫描，查找 `q` 这段文字，只读类型声明为 [`searchable`](../core/model/schema.mdx#schema-22) 的字段，所以助手交互的工具输出和注入的上下文不参与。

| 参数 | 只返回 |
| --- | --- |
| `q` | 必须给出。字段中含这段文字的 |
| `from`、`to` | 事实时间与范围相交的，规则和[查询观测](#observations)相同 |
| `resourceName` | 这种业务类型的 |
| `thingId` | 业务字段引用这个事物的，按成立的 Same-As 展开 |
| `speakerId`、`excludeSpeakerType` | 按说话人筛选，和[查询观测](#observations)相同 |
| `view` | 见[视图](#view) |

响应和排序与查询观测相同。

## 引用方 [#referrers]

[`GET /things/{thingId}/referrers`](/api/listThingReferrers) 和 [`GET /observations/{observationId}/referrers`](/api/listObservationReferrers) 列出引用目标的 Observation，也就是它的引用方。例如找一条判断有没有被否定，就列出引用它的 Review。接口只返回直接的引用方，更远的关系由读取方逐层查询。

查询 VS Code 的引用方，一页中的一项：

```json
{
  "observation": {
    "observationId": "01a12e31-9050-7000-8000-000000000120",
    "schemaRevisionId": "019e1bbb-ec00-7000-8000-000000000101",
    "observerId": "01a12e31-9050-7000-8000-000000000030",
    "speakerId": null,
    "observerDescriptionId": "01a12e31-9050-7000-8000-000000000130",
    "formation": "direct",
    "inputSetId": null,
    "replaces": [],
    "startAt": "2026-10-06T06:00:00Z",
    "endAt": "2026-10-06T08:00:00Z",
    "timeZone": "Asia/Shanghai",
    "recordedAt": "2026-10-06T08:00:01Z",
    "content": {
      "localApplicationId": "01a12e31-9050-7000-8000-000000000101",
      "name": "Visual Studio Code",
      "icon": {
        "digest": "sha256:3a7bd3e2360a3d29eea436fcfb7e44c735d117c42d1c1835420b6b9942dd4f1b",
        "mediaType": "image/png",
        "size": 612480
      }
    }
  },
  "references": [
    {
      "path": "/content/localApplicationId",
      "targetId": "01a12e31-9050-7000-8000-000000000101"
    }
  ]
}
```

- 目标按 id 精确匹配，不按 Same-As 展开。
- `path` 只返回在这个位置引用目标的 Observation。`resourceName` 只返回这种业务类型的引用方，例如应用识别 Observer 只读引用本机应用的前台时段。
- 匹配 `observerId`、`speakerId`、`observerDescriptionId`、`replaces`、业务字段中的 `reference`，以及 InputSet 的成员，见 [REFERENCE-2](../core/rules/references.mdx#reference-2)。使用某个 Schema 的数据通过 `resourceName` 列出。
- 每一项是引用方的完整 Observation。`references` 列出其中引用目标的每个位置，`path` 是从 Observation 根部写起的 JSON Pointer（[RFC 6901](https://www.rfc-editor.org/rfc/rfc6901.html)）。引用方通过 InputSet 引用目标时，`path` 是 `/inputSetId`。
- `view` 默认为 `current`，见[视图](#view)。
- 结果按引用方的 `observationId` 升序排列。`observationId` 是 UUIDv7，所以这也是形成的先后；`order=desc` 改为降序。翻页时沿用第一页的 `order`，游标与排序不符时返回 `400`。
- 目标已被删除时，照常列出引用方，读取方据此知道哪些数据的追溯不完整，见 [HISTORY-8](../core/rules/history.mdx#history-8)。身份从未出现过时返回 `404`。

## 一次工作 [#runs]

Agent 回答问题时自己决定读什么。[`POST /runs`](/api/createRun) 开始一次工作，得到 `runId`；读取时带上它，后端记下读过的 Observation；写入时带上它，InputSet 取这次的读取记录，Agent 不用再列，见 [EVIDENCE-9](../core/rules/evidence.mdx#evidence-9)。

```text
POST /runs                                  → { "runId": "…" }
GET  /search?q=…&runId=…
GET  /observations?thingId=…&runId=…
POST /writes   writes[0].runId = …
```

查询观测、搜索、对象视图、列出引用方、按 id 读取 Observation 都接受 `runId`。一次读取返回的每份 Observation 都算读过。程序化的 Observer 继续自己列 `inputs`。

## 分页 [#paging]

列出事物、列出修订、查询观测、搜索和列出引用方都分页。`limit` 是一页最多返回的项数，默认 100，最大 1000；列出引用方时，一份 Observation 连同它的全部位置算一项。响应中的 `next` 是下一页的游标，把它作为 `after` 传入就得到下一页；没有下一页时，`next` 为 `null`。游标的内容由后端决定，调用方原样传回；它绑定这次查询的条件和顺序，用在别的查询上时返回 `400`。
