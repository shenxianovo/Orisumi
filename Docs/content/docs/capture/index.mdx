新增或修改采集器前读这一页。进程和数据流见[架构](../overview/architecture.mdx)，各来源记了什么见左侧「来源」，怎么查能还原到哪见[覆盖与恢复](./recovery.mdx)。

## 采什么

只采关于人的。观测要能落到人身上：人的行为、人的身体状态，以及人为自己摆出的环境，比如开着的应用、打开的标签页、工作目录。注意力只在前台，但同一段时间开着哪些东西，说明人在做什么。

和人无关的数据是噪音，不采，比如网络流量、系统更新。能说明人在不在、观测是否连续的系统状态照常记，比如休眠、锁屏、权限变化。

## 原则

**初值 + 变化 = 任意时刻的状态。** 下面每一条都是为了让这个等式成立。

### 先定对象

每类对象一张身份表，记它是谁，以及永远不变的属性。比如下载的 URL 和开始时间、书签的创建时间。

不变的属性一开始可能不知道，后来可以从未知补成已知；已知之后不再改。

### 会变的属性只记初值和变化

第一次看到时记一行初值，之后只在值变了才记。值没变不写。

能一起记的放一张表，否则拆开。判断标准：来源会不会单独改、或单独缺其中一个。

- 下载的状态和完成时间总是一起变：放一张表。
- 下载的本地路径会单独变：单独一张表。
- 回合的开始时间不变，结束时间后来才有：开始时间放身份表，结束时间单独记。

拆对了，每张表的一行都能用一句话说清：“某对象的某组属性，在这次观测时变成了这个值”。

按怎么变拆表，不按长什么样拆表。日志里的条目写下就不变，各类型只是字段不同：Agent 日志每条事件一行，公共字段是列，各类型挑出的字段放进一张内容表的 `payload_json`；没挑内容的事件就没有内容行。来源加了新类型，只改挑字段的代码。

### 事件每次发生都记

按键、休眠、网页访问没有“当前值”，发生一次记一行，不去重。重试送来的同一次发生，靠事件 ID 去重。

### 未知和空要分开

NULL 只表示“不知道”，与 SQL 本身对 NULL 的理解一致。“知道它是空的”要写成明确的值。

| 情况 | 怎么记 | 例子 |
| --- | --- | --- |
| 读到了值 | 写这个值 | 窗口标题是 `README.md` |
| 读到了，来源明确说没有 | 写明确的空：文本（含来源 ID）用 `''`；外键或数字列加一列 `has_*` | 标题为空写 `''`；没有前台应用写 `has_app = 0` |
| 这次读不到 | 写一行 NULL，算一次变化 | 辅助功能权限丢了，读不到标题 |
| 来源这次没提这个字段 | 不写，沿用上一个值 | Chrome 下载回调只带了状态，没带路径 |
| 从没观测过，或采集断开 | 没有行；断开记在 `capture_runs` 和覆盖记录里 | 采集器启动前的情况 |

“读不到”必须写一行。不写的话，`current_*` 会一直显示上一个已知值，好像它仍然成立。

例外：某列在当前状态下本来就没有值，比如下载未完成时的完成时间、成功运行的错误信息。这时把它和决定它的列放在同一张表，用 `CHECK` 绑定两者；除此之外，NULL 一律是未知。

来源自己不区分“没有”和“读不到”时（比如应用的 bundle ID 返回 nil），只能记 NULL。

### 时间分两种

- `observed_at_utc_ms`：本地收到通知或读到来源的时间。
- 来源自己给的时间，按含义命名，例如 `visited_at_utc_ms`、`started_at_utc_ms`。来源没给就是 NULL，不拿观测时间顶替。

本库的自增 ID 和 `run_sequence` 只保证本库内的先后。

### 断开后重新起头

等式只在一条不断的观测链上成立。采集器停了、权限丢了、电脑休眠了，中间发生了什么我们不知道。如果直接接着记，查询会把断开的那段当成“没变”。

- 每段连续观测有自己的初值。恢复后能补读就先补读；补不齐就记下缺口，再重新记初值。
- `capture_runs` 一个常驻进程或一条浏览器连接记一行。结束时间和 `stop_reason` 一起写，因错误终止时 `error` 才有值；异常退出时两者留空，表示未确认，不用重启时间或查询时间补。
- 每轮提交时把 `confirmed_until_utc_ms` 更新到这一轮，说明至少确认到了哪。一轮失败就回滚，在 `capture_read_failures` 记下，运行继续。不为每一轮记覆盖，只在状态变化、失败和缺口时记。
- 运行中也可能缺权限、通道不可用、采样漏掉短暂变化，这些另外记。所以采集在运行，不等于全程都看到了。
- 没有新变化，只在链没断的前提下才能说明状态没变。

## 从哪里取数据

每类事实单独选取数方式，按这个顺序优先：

| 来源能力 | 怎么采 | 断开后怎么恢复 |
| --- | --- | --- |
| 可回放的日志 | 先回填，再按读取位置增量读 | 从已提交的位置接着读；来源已经删掉的部分记为缺口 |
| 变更通知 | 记初值，然后接上通知，记每次变化 | 重放还没送达的通知；补不了的区间记为缺口，重新记初值 |
| 只能读当前值 | 定时读，和上次比，变了才记 | 记下采样边界，恢复后重新记初值 |

后两种得到的“变化”可信度不同。通知送来的变化，时间接近真实。读当前值比出来的变化，只能说明“读的时候已经变了”：时间是读取时间，两次读取之间的 A→B→A 会整个丢掉。通知只说“有变化”、要再去读值时，读到的结果也属于后一种。用了后两种的，在该来源的页面写明丢什么。

**初值和通知要接上。** 先订阅通知并缓存，再读快照，然后把快照之后的通知接上。顺序反了，读快照和开始监听之间的变化会丢。来源做不到原子衔接时，用序号、重试或读后核对补上。

**定期核对**只用来纠正当前状态、发现漏掉的通知；值没变就不写。它补不出断开期间的 A→B→A。批量写入、重试、超时这些定时器和采样频率分开设置。

## 写入与恢复

- 一次观测产生的几条事实，在同一个事务里提交，各表的行共享同一个观测标识。读取游标和事实一起提交，否则会出现游标前进了但事实没写，或反过来。
- 保留能回到来源核对的上下文，比如日志的文件和行号、来源对象的 ID。
- 重试不能重复入库。可重试的跨进程投递用稳定的事件 ID；接收端提交后再确认，确认后才从持久队列删除。确认丢了，重发也安全。
- 日志游标记文件身份和读取位置，要处理截断、替换、移动和末尾的半行，`Shared/Capture` 的 `JsonlReader` 做这些；来源自己发现文件、挑事实。文件变化通知只用来触发读取，事实以文件内容为准。
- 输出库重建后，读取游标和初值都从新库开始：能回放的历史重新补读，其余重新记初值。
- 读取游标（`_source_cursors`、`_rollout_cursors`、`_history_cursors`）、浏览器投递进度（`_browser_deliveries`、`_browser_snapshots`）、`confirmed_until_utc_ms` 和扩展待发队列是采集进度，可以原地更新，不算历史事实。

## 查询视图

- `*_history` 给出每次观测后的完整状态；`current_*` 给出最后已知状态。
- 最后已知状态不说明来源现在还在、还能读到。
- 需要缓存时，缓存必须能从事实表重建。
- 不同来源库的本地 ID 不能直接关联。跨来源关联时核对设备、对象生命期和时间。

## 数据库结构

每个来源写自己的库，放在哪、写哪个见[存储](../overview/storage.mdx)。结构定义放在采集器项目的 `Schema/`：

| 路径 | 内容 |
| --- | --- |
| `Tables/` | 每张表一个 SQL 文件，含字段、键和约束 |
| `Indexes/` | 普通索引，按所属表分文件 |
| `Views/` | 每个视图一个 SQL 文件 |

构建时自动收集这些文件，按表、索引、视图的顺序执行，同组按文件名排序，不用登记清单。这些文件只定义结构；导入时用的临时视图留在采集代码里。

C# 采集器通过共享项目 `Shared/Capture` 的 `CaptureWriter` 写入：它用 `CollectorDatabase.Open` 打开库，新库按共享项目和采集器程序集里的 SQL 建结构，一轮怎么走见[架构](../overview/architecture.mdx#一轮写入)。它在运行期间持有单写入锁（`state/locks/<来源>.writer.lock`，浏览器按配置各一把），同一存储目录下第二个写入方直接失败。

没有任何用户对象的空库在一个事务里建结构，失败时回滚；已有对象的库原样使用，不核对结构。打开连接时启用外键、3 秒锁等待和 WAL。

每个库都提供 `capture_coverage` 视图，前六列依次是 `scope`、`mode`、`started_at_utc_ms`、`stopped_at_utc_ms`、`evidence`、`detail`，含义见[覆盖与恢复](./recovery.mdx)；来源自己的列跟在后面。

每个库还有 `Shared/Capture/Schema/` 里的共享表，构建时和来源自己的 `Schema/` 合在一起按文件名执行：

- `database_identity`：建库时在同一事务里写一行，之后不变。`database_id` 是随机 32 位十六进制，等于库文件名，库在设备间合并时靠它区分；`platform`、`hardware_uuid` 是存储选库时绑定的建库主机，读不到硬件 UUID 时为空，含义见[多设备](../overview/devices.mdx#身份)。
- `host_observations`：运行开始时由 `Orisumi.Platform.HostIdentity` 读到的主机原始标识，包括硬件 UUID、主机名、型号、系统版本、启动 ID、系统用户和存储目录；读不到的为空。和上一行完全相同时不写新行，所以重启开机或换了存储目录才会多一行。

`capture_runs`、`capture_read_failures` 也是共享表。`capture_runs.host_observation_id` 指向这次运行开始时的主机观测，和运行在同一事务里写入；`collector_version` 记写这次运行的采集器版本（程序的版本号加提交号），加这一列之前的运行为 NULL。

结构没有版本号，代码里不做迁移；SQLite 文件自带建表语句，旧库按它自己的结构读。改结构时停掉对应采集器，能迁移的用一次性脚本迁移现有库，再启动：只增不改的变更（加表、加可为空的列）不影响已有数据，新加的部分在此前没有行，即未观测。开发期已有数据可以删：破坏性更改不必写迁移，删掉 `state/current/<来源>.json`，下次采集新建库，旧库留在原处只读，不要时整个删掉。旧库不会在打开时被拒绝，要到写入时才在 SQL 层报错。原地迁移保留库 ID；已拷到其他设备的副本，由再次导出的同 ID 快照替换。macOS 库总是建完整结构，选项只控制哪些通道采集和写入。

## 开发与验证

1. 每类事实先想清楚：对象身份、取数方式、时间含义、能还原到什么程度。
2. 先做好初值衔接、提交确认和中断恢复，再接启动和查询。
3. 按实际风险测：A→B→A、静止时不重复写、重复投递、提交前后崩溃、恢复后的缺口。日志来源另测半行、替换和截断；采样来源另测计数重置和身份变化。

测试命令见[开发入口与命令](../development/index.mdx#验证)。

## 新增采集器

每个采集器是一个独立程序 `orisumi-<来源>`，单独构建、单独定版本。采集器共享建库、`CaptureWriter`、`JsonlReader`、参数绑定和命令入口这些工具，不共享采集流程：取数、监听、游标和写哪些表由各来源按上面的原则自己定。

宿主 `orisumi` 不引用任何采集器，只通过 `describe` 认识它。`describe` 输出一个 JSON 对象：名字（即 `observations/` 下的目录名）、版本和常驻采集的参数。`capture start` 用这些参数把每个采集器装成 LaunchAgent，见[安装与启停](../development/release.mdx#安装与启停)。数据在别的程序里的来源（如 Chrome）由那边的插件连到常驻的采集器，采集器不由那个程序拉起。

采集器之间、采集器与宿主之间的约定只有：存储布局、共享表、`capture_coverage` 的前六列和 `describe`。改这些要所有采集器跟着改，尽量不动。

1. 建 `Collectors/<来源>/Orisumi.Collectors.<来源>.csproj`。`Collectors/Directory.Build.props` 把它构建成程序 `orisumi-<来源>`，并提供框架、SQLite、`Schema/` 打包、共享项目 `Shared/Capture`（写入和命令）和 AOT 设置；项目文件只写来源自己的依赖和 `Version`。代码要能 Native AOT 发布：JSON 用源码生成，不靠反射；`dotnet build` 报的 AOT 警告必须为零。
2. 按上面的约定写 `Schema/`，包括 `capture_coverage`；运行表和读取失败表是共享的，不用写。
3. 写 `Program.cs`：用 `new Collector("<来源>", typeof(…).Assembly)` 说明来源名和程序集（版本和 `Schema/` 从这里取），用 `CollectorCommand.Create` 建根命令并给出常驻采集的参数，再加来源自己的命令，交给 `CollectorCommand.Run`。
4. 在 `Orisumi.slnx` 登记项目。宿主从 `describe` 发现采集器，发布也按 `Collectors/` 下的目录找组件，不用另外登记。
5. 加 `Tests/<来源>Checks.cs`，并登记到[验证](../development/index.mdx#验证)。`SchemaChecks` 会核对项目目录与 `Orisumi.slnx` 是否一致、`describe` 的名字是否等于目录名的小写，以及 `capture_coverage` 的列。
6. 在 `capture/sources/` 加一页写它记了什么、丢什么，在[覆盖与恢复](./recovery.mdx#恢复边界)补一行恢复边界，在[命令](../development/index.mdx#命令)补命令。
